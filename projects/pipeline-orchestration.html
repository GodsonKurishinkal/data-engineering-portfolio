Case study 2 of 6 · Scheduling

Job scheduling with install-time validation

A scheduling layer on top of Windows Task Scheduler. One YAML file defines every job, a validator checks the job graph before anything is installed, and each job checks that its upstream data is fresh before it runs.

01

The problem

Everything runs on a single Windows host. There is no cluster or container runtime, so Airflow, Prefect and Dagster were not available. That left the OS scheduler, which has no concept of a dependency.

Dependencies were therefore expressed as start times: if the upstream extract usually finishes by 00:05, schedule the transform at 00:10. This failed in several ways:

  • Several reporting jobs were scheduled into the same few minutes against one reporting server. Some failed. Others received an error page that was saved as if it were data.
  • A multi-part extract continued past a failed part and wrote an incomplete partition. Later runs skipped it because the partition already existed.
  • A filtered read returned zero rows without an error, because the reader and the writer used different letter case for the partition keys.
  • A bot reported a UI timeout. The actual cause was the server behind it running out of memory.

In each case the failure was either not visible or attributed to the wrong cause. A schedule based on start times cannot report that it is wrong.

Config. One YAML file lists every job with its schedule, dependencies, retries and freshness requirements. Changing a job is a diff in that file.

Validator. Runs before anything is written to the machine and refuses the install if any of nine checks fails: duplicate IDs, malformed IDs, unknown dependencies, cycles, time collisions inside a folder, dependencies scheduled after their dependents, missing commands, paths outside the project root, and unsafe shell arguments.

Runner. Every job goes through the same runner. It checks upstream freshness, waits for a bounded window if the upstream is late, then runs the job with retries and logs each attempt. If the upstream data is stale or missing, the job does not run and an alert is sent.

Task Scheduler. Holds only a trigger time and the same command for every task.

03

Key decisions

ADR-007 on GitHub

Build the graph layer, keep Task Scheduler for execution

Task Scheduler already runs things reliably. What was missing was a way to express dependencies and check them. I built that part and left execution alone.

Trade-off: I wrote cycle detection and topological ordering myself, which an orchestration framework provides. They need their own tests; most of the 43 tests in the private work code cover this.

Decision 02

Check the graph at install time

A cycle or a time collision can be found by reading the config. The nine checks run before any task is registered, so these errors do not reach runtime.

Trade-off: the checks are conservative and sometimes refuse a schedule that would have been fine. Relaxing one means changing code and a test.

Decision 03

Freshness checks instead of time offsets

"Run five minutes after the upstream" is a guess about duration. A freshness check states the requirement directly: this job needs data no older than X. If the upstream is late, the job waits for a bounded window. If the data is stale or missing, it alerts and does not run.

Trade-off: a slow upstream holds the downstream job's slot for the length of the wait instead of failing fast.

Decision 04

One command for every task

Every registered task runs python -m orchestration run <id>. Nothing job-specific is stored on the machine, so the full set of scheduled tasks can be rebuilt from the repository with one command.

Trade-off: the layer is tied to Windows. I have not tested it on another host, and the trigger mechanism would need replacing there.

04

Implementation

Each of the nine checks has its own error code, so a refused install names the rule that failed and the schedule that failed it. A simplified version of the list:

orchestration/validator.py (simplified) Python scroll → 
# Checks run on the whole schedule graph before install.
CHECKS = [
    ("E_DUP_ID",        _unique_ids),              # two jobs, one name
    ("E_ID_FORMAT",     _id_format),               # unparseable id
    ("E_DEP_UNKNOWN",   _deps_resolve),            # dependency does not exist
    ("E_CYCLE",         _no_dependency_cycle),     # A → B → A
    ("E_TIME_CONFLICT", _no_time_conflicts),       # same slot, same host
    ("E_DEP_ORDER",     _dependency_ordering),     # parent runs later
    ("E_CMD_MISSING",   _command_present),         # nothing to run
    ("E_PATH_ROOT",     _paths_within_root),       # path outside the project
    ("E_UNSAFE_ARG",    _args_allowlisted),        # shell injection
]

The runner returns a different exit code for "upstream missing", "upstream stale" and "the job failed", so an alert says which of the three happened.

05

What changed

  • Cycles, time collisions and wrong dependency order are now install-time errors. They no longer show up as overnight incidents.
  • All 150+ jobs run through the same runner, so a change to retry or logging behaviour applies to every job.
  • The overlapping window that overloaded the reporting server is gone, because the validator rejects time collisions.
  • Alerts separate "upstream was not ready" from "the job failed".

This work did not make anything faster. It removed a group of failures that used to go unnoticed until a report was wrong.

06

What I'd do differently

Test the jobs, not only the scheduler

The 43 tests cover the orchestration layer. The extraction and transform code it triggers has far fewer. I tested the part I was building and left thinner coverage on the code that touches the source systems.

Requeue instead of waiting

A late upstream occupies the downstream job's slot for the whole bounded wait. Requeuing would free the host, at the cost of a more complicated runner.

Add a shared check for unsafe patterns

The same unsafe pattern, a side effect that a comment said was disabled while the code still performed it, appeared more than once. A shared check would have caught the repeat.

Finish the path migration

Some modules still build lakehouse paths directly instead of going through the dataset registry.
