01

The problem

The platform runs on a single Windows host. No cluster, no container runtime, no budget for either — which rules out Airflow, Prefect and Dagster before the conversation starts. What was left was the OS scheduler, and the OS scheduler has no concept of a dependency.

So dependencies were expressed as arithmetic. If the upstream extract usually finishes by 00:05, schedule the downstream transform at 00:10 and hope. That works until it doesn't, and the ways it stopped working were instructive:

  • Ten reporting jobs were scheduled between 00:01 and 00:11 against one BI server. The server buckled. Some jobs got an HTTP 407; others were served an HTML error page that was saved with a .csv extension and counted as records.
  • A report pulling from two URLs continued past a failed second URL, wrote an incomplete partition, and then refused to re-pull — because the partition existing was treated as the partition being complete.
  • A filtered read returned zero rows, silently, for weeks: the reader filtered on YEAR/MONTH/DAY while the writer partitioned on year/month/day.
  • A bot reported a 30-second UI timeout. The real cause was a std::bad_alloc on the reporting server — the timeout was a symptom being read as the diagnosis.

The common thread isn't that jobs failed. It's that the failures were invisible or misattributed. A wall-clock schedule can't tell you it's wrong. It just produces a plausible-looking file.

02

The system

One YAML file is the source of truth for every job. A validator refuses to install a graph that violates any of nine invariants. Task Scheduler is demoted to a dumb trigger — every one of the 166 tasks has the same action — and all the intelligence lives in version-controlled, testable Python.

The validator runs before anything is written to the machine. Duplicate IDs, malformed IDs, unknown dependencies, cycles, time collisions inside a folder, dependencies scheduled after their dependents, missing commands, paths escaping the project root, and unsafe shell arguments — nine ways a schedule can be wrong, all of them refused at build time.

The runner is the single runtime contract every job shares. It resolves freshness checks first, waits for a bounded window if the upstream is late, then executes with retries and per-attempt logging. A job that would have run on stale data doesn't run at all — it alerts instead.

Task Scheduler holds nothing but a trigger time and one identical command. Moving a job, adding a dependency, or changing a retry count is a diff in a YAML file, not a click in a GUI on a server nobody wants to log into.

03

Key decisions

A validator, not a frameworkADR-007

An orchestrator is mostly two things: a way to express a graph, and a way to run it safely. I didn't need the second — Task Scheduler already runs things. I needed the first, plus guarantees. So I built the graph layer and left execution alone.

Trade-off: I hand-rolled cycle detection and topological ordering that a framework gives away free — and now have to test them myself. That's what the 43 tests are for.
Fail at install, not at 2amDecision 02

A cycle or a time collision is a static property of the config. There's no reason to discover it at runtime, in the dark, through a downstream report being wrong. The nine invariants run before a single task is registered.

Trade-off: the invariants are conservative and occasionally refuse a schedule a human knows is fine. Loosening one means changing code and a test, deliberately — which is the point.
Freshness gates, not wall-clock offsetsDecision 03

"Run five minutes after the upstream" encodes a guess about duration. A freshness check encodes the actual requirement: this job needs data no older than X. If the upstream is late, wait a bounded window; if it's stale or missing, alert and don't run.

Trade-off: a slow upstream now holds the downstream job's own slot for the length of the wait, instead of failing fast. Late beats wrong, but it isn't free.
One uniform action for all 166 tasksDecision 04

Every registered task runs python -m orchestration run <id>. Nothing job-specific lives on the machine. The scheduler estate is reproducible from the repo, and a corrupted Task Scheduler can be rebuilt from one command.

Trade-off: the orchestration layer is Windows-bound. Portable in principle, untested in practice — the trigger mechanism would need replacing on any other host.
04

Implementation

The runner is the whole runtime contract in about forty lines. Gate on freshness, build the command, run it with retries, log every attempt. Every job in the estate goes through exactly this path — there is no second way to run something.

orchestration/runner.py Python 
def run(schedule_id: str) -> int:
    registry = load(CONFIG_PATH)
    sched = registry.by_id(schedule_id)
    log = Log.for_name(f"orchestrator.{schedule_id}")

    if not sched.enabled:
        log.info(f"Schedule {schedule_id} disabled — skipping")
        return 0

    # Freshness gate. Each check may opt into a bounded poll-wait.
    # The first failing check short-circuits and alerts — the job
    # does not run on data it was told not to trust.
    for fc in sched.effective_freshness_checks:
        status = _wait_for_freshness(fc, log)
        if status == "missing":
            send_failure_alert(sched, reason="upstream_missing")
            return 2
        if status == "stale":
            send_failure_alert(sched, reason="upstream_stale")
            return 3

    # Execute with retry. Distinct exit codes so the caller can tell
    # "upstream wasn't ready" from "the job itself broke".
    cmd = _build_cmd(sched, registry.settings)
    for attempt in range(sched.retries + 1):
        result = subprocess.run(cmd, cwd=sched.working_dir, capture_output=True)
        if result.returncode == 0:
            return 0
        log.warning(f"attempt {attempt + 1} failed", stderr=result.stderr)
    return 1

The nine invariants live next to it in the validator, each with its own error code so a failed install says exactly which rule was broken and which schedule broke it.

The honest framing: this work removed a class of silent failure rather than making anything faster. Nothing here reduced a runtime. What it changed is that a wrong schedule now fails loudly at build time instead of producing a plausible file at 2am.

06

What I'd do differently

Lint the dangerous idiom, don't fix it twice

The same email-safety bug — a live send with the draft call commented out beneath a comment claiming "draft only" — was found and fixed independently in two unrelated projects. One shared check asserting no unguarded send would have caught it the first time and prevented the second.

Test what's scheduled, not just the scheduler

43 tests sit on the orchestration layer and far fewer on the extraction and transform code it triggers. I hardened the part I was actively building and left thinner coverage on the parts that actually touch the source systems.

Yield the slot instead of holding it

A late upstream currently occupies the downstream job's window for the whole bounded wait. Requeuing rather than blocking would free the host, at the cost of a more complicated runner.

Finish the path migration

Two modules still carry TODOs pointing at hardcoded lakehouse paths that should route through the dataset registry. Small, known, and exactly the debt the registry exists to eliminate.
