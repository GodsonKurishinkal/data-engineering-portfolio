01

The problem

Supply chain reporting was assembled by hand from ERP, WMS, BI reports, POS and Excel exports. Each source had its own format and schedule.

  • Daily extraction took 4+ hours before any analysis could start.
  • Reports were 24–48 hours behind the source systems.
  • Analysts spent about 60% of their time reconciling fields.
  • There was no lineage, so every data issue had to be traced by hand.
02

What I built

Three layers of Parquet files on one Windows machine, processed with Polars and queried with DuckDB. Each layer has one job.

Bronze holds each source extract as it arrived, untransformed. It is the record I reprocess from.

Silver is schema-enforced, deduplicated and typed. The three-tier data-quality checks run here, before anything reaches Gold.

Gold is a Kimball star schema with 10+ fact tables and 6+ conformed dimensions. Business logic lives here, and Power BI models and forecasting read from it.

50+ pipelines feed these layers. Each one is a YAML config run by a shared extract, transform and load framework, so a behaviour change is a text diff.

03

Key decisions

ADR-001 on GitHub

Polars over Pandas

The nightly Silver transforms had to finish inside a fixed window. Polars was faster than Pandas on these workloads and used less memory through lazy evaluation.

Trade-off: a smaller community and fewer worked examples to lean on.

ADR-004 on GitHub

Hive-partitioned Parquet, not Delta

There was no Spark or Databricks runtime. Plain Parquet partitioned by extract_date was fast enough with DuckDB and Polars and needed no extra platform.

Trade-off: no time travel or ACID guarantees on Bronze. Backfills are explicit partition overwrites.

ADR-005 on GitHub

Configuration-driven ETL

Each pipeline is a YAML config on top of a shared base class. Schema, quality rules and load mode (FULL or INCREMENTAL) are declared, not coded per pipeline.

Trade-off: a steeper start for anyone new to the framework. Templates and reviewed changes reduce it.

ADR-007 on GitHub

Windows Task Scheduler for orchestration

Airflow needs infrastructure this setup did not have. I used the OS scheduler that was already there, with structured logs and Teams alerts on failure. The scheduling layer is described in Job scheduling with install-time validation.

Trade-off: no DAG view. A small Streamlit status board reads the pipeline log table instead.

Example pipeline config

A simplified example of one pipeline definition. The engine reads the file and runs extract, validate, transform and load.

pipelines/inventory_daily.yaml YAML scroll → 
# Simplified illustration, not the production file.
pipeline:
  name: "inventory_daily"
  source:
    type: "bi_server"
    query: "SELECT * FROM inventory_snapshot WHERE snapshot_date = :d"
  destination:
    layer: "bronze"
    format: "parquet"
    partition_by: ["extract_date"]
  quality:
    required: ["sku_id", "location_id", "on_hand_qty"]
    rules:
      - "on_hand_qty >= 0"
      - "extract_date <= today"
  load_mode: "INCREMENTAL"
  schedule: "0 6 * * *"   # 06:00 daily

06

What I'd do differently

Start with the data contract

Shipped
I built Bronze first and wrote schemas later, then spent time on downstream fixes that a declared schema would have caught at the boundary.

Schemas are now declared up front as typed column specs and enforced at the Bronze → Silver gate. Trade-off: each new source needs an extra declaration, and the registry can drift from reality.

Add lineage earlier

Lineage is still local to each pipeline. An OpenLineage-compatible emitter from the start would have made cross-pipeline debugging cheaper.

Delta, with the right runtime

Plain Parquet fits this runtime, but time travel and ACID on Bronze would remove some reprocessing risk.

Semantic layer as code

Business definitions live in Power BI DAX. A dbt-style layer above Gold would make them reusable and testable outside BI.
