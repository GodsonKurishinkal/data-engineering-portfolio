Browser automation for systems without APIs

Four bots that log in to systems with no API, run the exports a person used to run by hand, and land the files in Bronze. They share one base class for retries, failure screenshots and alerts.

01

The problem

Four source systems (WMS, BI reporting server, ERP and a POS reporting portal) had no API. The only way to get data out was to log in and export a report from the screen.

  • Every morning someone logged in to all four systems and ran the exports by hand.
  • The files went from Downloads to shared folders and were then imported manually.
  • This took 4+ hours before any analysis could start.
  • Mistakes in the manual steps broke reports downstream without anyone noticing.

The systems were not going to be replaced and APIs were not planned, so I automated the screen steps.

02

What I built

One abstract base class defines what every bot does: log in, extract, save, clean up. Each bot implements only the parts specific to its system. The base class provides the rest:

  • Retries with backoff for network errors, slow pages and session timeouts.
  • A screenshot and page capture on every failure, so a changed screen can be seen instead of guessed at.
  • Waits on element visibility with a timeout per step, instead of fixed sleeps.
  • Credentials read from an encrypted store and kept out of logs.
  • An alert on failure, and an execution log of steps, timings and record counts.

The bots were built on Selenium. The ones that drive a web page have since moved to Playwright. PyAutoGUI handles the desktop UI that has no DOM.

04

Key decisions

Decision 01

A shared base class instead of four scripts

The first bot was a single script. Four scripts would have meant four copies of the retry logic, credential handling and debugging conventions. A base class keeps those in one place.

Trade-off: writing a new bot means learning the framework first. A template bot and notes reduce that.

Decision 02

Browser automation where there is a DOM, PyAutoGUI where there is not

A browser driver is precise when the target is a web page. It cannot drive a desktop or terminal-style UI, so those screens use PyAutoGUI with image matching. The bot structure is the same either way.

Trade-off: screen automation is fragile. A UI redesign breaks a bot, and the PyAutoGUI bots break most easily. The failure screenshot shows what changed.

Decision 03

Headless only where it works

Some of the older screens do not render without a visible window. Each bot sets whether it runs headless.

Trade-off: the bots need a dedicated Windows machine with a desktop session and cannot run in a container.

Decision 04

Land raw, transform later

A bot writes exactly what it extracted to Bronze, with metadata, and stops. Parsing and cleaning happen downstream, where a failure is cheap to re-run. A change to a bot does not change every model that depends on it.

Trade-off: Bronze carries more columns than the models need.

Implementation

The base class owns the run order and the error handling. A subclass supplies the login and the extract.

from abc import ABC, abstractmethod

# BotConfig and ExtractResult are small dataclasses defined elsewhere.

class BaseBot(ABC):
    """Shared run order for all bots."""

    def __init__(self, config: BotConfig):
        self.config = config
        self.driver = None

    def run(self) -> ExtractResult:
        try:
            self._initialize_driver()
            self._login()
            rows = self._extract()
            self._save_to_bronze(rows)
            return ExtractResult(success=True, records=len(rows))
        except Exception as e:
            self._capture_screenshot()
            self._send_alert(str(e))
            raise
        finally:
            self._cleanup()

    @abstractmethod
    def _login(self) -> None: ...

    @abstractmethod
    def _extract(self) -> list[dict]: ...

06

What changed

  • The 4+ hours of manual collection each morning no longer happens. The four bots run unattended and the extracts are in Bronze before the working day starts.
  • A failed run produces a screenshot and an alert, so a changed screen is found the same day.
  • Moving to selectors based on labels and roles, with fallback locators, reduced how often a small UI change broke a bot. I did not measure by how much.
07

What I'd do differently

Playwright instead of Selenium

Shipped
With Selenium, every slow-rendering report needed sleep-and-retry workarounds.

The bots that drive a web page now run on Playwright. Its auto-waiting removed most of those workarounds, and network interception lets a bot detect a server error page before it is saved as data. The desktop-UI bot stays on PyAutoGUI. Trade-off: two automation libraries to keep current.

Isolate the bots from each other

All four run on one shared Windows host, so one stuck bot can hold up another. Separate runners with pinned browser versions would contain a failure.

Ask for real integrations earlier

Bots are a stopgap. I should have started asking the system owners for proper exports or APIs on day one.
