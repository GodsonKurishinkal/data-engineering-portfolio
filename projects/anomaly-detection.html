Three-tier data-quality checks

Schema, business-rule and statistical checks between the Bronze and Gold layers of the lakehouse. Each tier checks a different kind of failure and responds differently: block the batch, flag the rows, or raise an alert.

01

The problem

Bad rows in supply chain data lead to wrong operational decisions: a corrupted inventory record can trigger a purchase order nobody needed, and a missing dimension key breaks the reports built on top.

  • Source systems sent nulls where quantities should exist.
  • Dimension tables arrived with duplicate or missing keys, which broke joins.
  • Sales spikes caused by system glitches looked the same as real demand.
  • Gradual drift went unnoticed for months.
  • When something broke, nobody could say which records were at fault.

No single method covers all of these. Schema checks miss behavioural problems, business rules miss statistical drift, and outlier statistics miss referential integrity.

01
Schema validation
Bronze → Silver · Blocks the batch

Enforces the data contract before a row enters Silver. If the schema check fails, the batch is refused.

  • Nulls in required fields
  • Types against the declared schema
  • Referential integrity (FK → PK)
  • Range constraints (e.g. qty >= 0)
  • Primary-key uniqueness
02
Business rules
Silver → Gold · Flags rows, load continues

Domain checks that a schema cannot express. Failing rows are flagged and written to a quarantine partition; the rest of the batch loads, so a few bad rows do not stop operations.

  • Cross-field consistency (ship_date ≥ order_date)
  • On-hand quantity and safety stock not negative
  • Dimension keys match across facts
  • No future-dated transactions
03
Statistical outliers
Gold, on a schedule · Alerts and logs

Runs over Gold facts. Finds values that pass the schema and the rules but are still unusual: single outliers, step changes and slow drift.

  • Z-score and modified Z-score (MAD)
  • IQR fences and percentile bounds
  • Rolling coefficient of variation
  • Period-over-period spikes and drops

The public code numbers things differently. Above, tiers are numbered by response. In the code, the blocking check lives in SchemaEnforcer, outside the detector module. The detector numbers its own tiers by method (validation, outliers, volatility), so its tier 1 is the business-rule layer here, and its tiers 2 and 3 are both inside tier 03 here. The detector never halts a pipeline; it reports, and the caller decides.

03

Detection methods

Tier 3 uses several methods because each one fails on some kinds of data.

Z-score

Parametric
Standard deviations from the mean. Fast; works when data is roughly normal.
z = (x − μ) / σ

Modified Z-score

Robust
Median and MAD instead of mean and standard deviation, so the outliers do not distort the baseline.
M = 0.6745(x − x̃) / MAD

IQR fences

Non-parametric
Quartile bounds with no distribution assumption. The default for skewed data.
[Q1 − 1.5·IQR, Q3 + 1.5·IQR]

Rolling CV

Volatility over time
Coefficient of variation over a moving window. Flags a change in how volatile a series is.
CV = σ / μ (rolling)

Percentile bounds

Empirical
Flags values outside a configured quantile pair. Crude, but a planner can understand the threshold.
x < P₁ or x > P₉₉

Spike / drop

Period over period
Compares this period's total with the previous one and flags moves past a percentage threshold.
Δ% = (curr − prev) / prev
04

Key decisions

Three simple tiers instead of one modelDecision 01

A schema error needs a fast yes/no check, not a learned model. Three small layers are easier to reason about and debug than one ML-based detector.

Trade-off: each tier has to be tuned separately.
Quarantine flagged rows, don't delete themDecision 02

Flagged rows go to a quarantine/ partition. Some "anomalies" are real events, such as a promotion or a store opening, and need to be looked at.

Trade-off: extra storage, and the quarantine needs someone to review it.
Severity levels on alertsDecision 03

On its first day, tier 3 sent 100+ chat alerts. I tuned thresholds per metric and tagged each alert INFO, WARN or PAGE, which brought it down to about 10 a day that needed action.

Trade-off: the severity mapping is manual and per metric.
Thresholds that depend on the calendarDecision 04

A large sales spike during a promotion is expected. Thresholds vary by weekday, holiday and season, which cut false positives.

Trade-off: it needs an events calendar that someone has to maintain.
05

Implementation

Each metric has a config. The detector picks the configured method and returns a boolean mask. A simplified version of one method:

Simplified illustration Python 
import numpy as np

def modified_zscore(data: np.ndarray, threshold: float = 3.0,
                    min_samples: int = 30) -> np.ndarray:
    """Return a boolean mask of outliers."""
    if len(data) < min_samples:
        return np.zeros(len(data), dtype=bool)
    median = np.median(data)
    mad = np.median(np.abs(data - median))
    m = 0.6745 * (data - median) / (mad + 1e-10)
    return np.abs(m) > threshold

Results

07

What I'd do differently

Declare rules as data

Tier-2 rules started as Python functions. Moving them to YAML earlier would have let analysts add rules themselves.

Baseline before alerting

I tuned thresholds after the alerts started. A two-week run with alerts muted would have given better starting thresholds.

Review the quarantine

Quarantined rows piled up. A weekly triage with labels (real event, bad data, fix upstream) would have closed the loop.
