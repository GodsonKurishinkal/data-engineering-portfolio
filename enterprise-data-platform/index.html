ETL framework components (public code)

A Python library of the building blocks I use for ETL: extractors, a schema enforcer, Parquet and DuckDB loaders, and data-quality detectors. Built on Polars and DuckDB.

StatusAlpha · partly tested
StackPython · Polars · DuckDB
Tests33 · run in CI
LicenseMIT

This is the only write-up with public code. It is a component library, not a running platform: the repository has no pipeline entry point, sample data or pipeline configs, and the extractors and loaders are untested.

01

What's in the repo

About 5,000 lines of Python in two packages, plus design documents. The source is on GitHub.

etl_framework/

Extract, transform, load
Base classes and implementations for database, API and browser-automation extractors; a schema enforcer and a data cleaner; a Hive-partitioned Parquet writer and a DuckDB loader.

data_quality/

Validation and outliers
A rule-based validation engine and an anomaly detector with z-score, modified z-score, IQR and percentile methods, plus spike and volume checks.

docs/architecture-decisions/

Seven ADRs
Polars over Pandas, DuckDB for analytics, the Bronze/Silver/Gold layout, Parquet with Hive partitioning, config-driven pipelines, browser automation, and Task Scheduler.

architecture/

Design notes
Layer specifications and a data-flow description. These describe a design; the pipelines they describe are not in this repository.
02

What is tested

33 tests cover the schema enforcer and the anomaly detector. Coverage on those two modules is 67%. Across the whole package it is 20%. The tests run in GitHub Actions on every pull request.

To reproduce, from the enterprise-data-platform folder:

Run the tests shell 
pip install -e ".[dev]"
pytest tests/ --cov=etl_framework --cov=data_quality
03

Known gaps

  • The extractors, the loaders and the validation engine have no tests. They need a live database, portal or browser to exercise, and none is provided here.
  • Nothing runs end to end. There is no entry point, sample data or pipeline config.
  • The lint and type checks configured in the Makefile currently fail.
  • Dependencies are not pinned and there is no lock file.
04

Architecture decisions

Each decision is recorded as an ADR in docs/architecture-decisions/ with its context, the alternatives and what it cost. Three of the seven:

Polars over PandasADR-001

Arrow-backed, multi-threaded and lazy, with native Parquet scans. Cost: a smaller ecosystem, and a learning curve for anyone used to Pandas.

DuckDB for analyticsADR-002

Queries Parquet files in place with standard SQL and needs no server. Cost: single-user, with limited support for concurrent writes.

Parquet with Hive partitioning, not DeltaADR-004

Plain files that both Polars and DuckDB read, with no Spark runtime. Cost: no ACID guarantees and no time travel.
